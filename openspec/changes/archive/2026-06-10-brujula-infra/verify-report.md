## Executive Summary

The brujula-infra change implements a comprehensive GCP infrastructure migration from the current VPS-based Docker Compose setup to Cloud Run (API/Web), Compute Engine (Celery worker), Cloud SQL (PostgreSQL), Memorystore (Redis), Cloud Storage (uploads), and an HTTPS Load Balancer. 

All **30+ Terraform files** across 9 modules exist with proper structure (main.tf + variables.tf + outputs.tf). All **6 shell scripts** pass `bash -n` syntax checks. The **Dockerfile** is properly Cloud Run-compatible with `--break-system-packages` and `PORT` env var support. The **config.py** has GCS support fields added. All **3 workflow files** exist.

Two minor issues found in GitHub Actions workflows (stray braces) that would cause runtime failures. No blocking structural issues — the Terraform modules are correctly wired via `main.tf`, all outputs connect to their expected inputs, and the architecture matches the design document.

## Issues Found

### 🔴 CRITICAL (Blocking)

1. **Stray closing brace in deploy-api.yml (line 103) and deploy-web.yml (line 104)**
   - **File**: `.github/workflows/deploy-api.yml` line 103, `.github/workflows/deploy-web.yml` line 104
   - **Code**: `SERVICE="${{ env.SERVICE_NAME }}-${ENV }}"` has an extra `}` after `${ENV}`
   - **Impact**: The `SERVICE` variable will have a trailing `}` character, causing `gcloud run deploy` to fail with an invalid service name
   - **Fix**: Change to `SERVICE="${{ env.SERVICE_NAME }}-${ENV}"` (remove the stray `}`)

2. **Hardcoded Redis IP in deploy-api.yml (line 97)**
   - **File**: `.github/workflows/deploy-api.yml`
   - **Code**: `REDIS_URL=redis://10.0.0.2:6379/0` is hardcoded as an env var
   - **Impact**: Redis IP is not guaranteed to be 10.0.0.2 — depends on subnet allocation. If the VPC subnet or Memorystore allocation changes, the connection breaks silently
   - **Fix**: Retrieve Redis IP from Terraform output or `gcloud redis instances describe` dynamically

### 🟡 WARNINGS (Should Fix)

1. **Load balancer uses host-based routing instead of path-based**
   - **Spec**: tasks.md 3.3 specifies `/ → web, /api/* → api`
   - **Implementation**: Host-based: `api.brujula.app → api`, `brujula.app → web`
   - **Impact**: Not a bug — host-based routing is architecturally cleaner. But differs from the agreed spec. Document this as a design decision change.

2. **APP_SECRET_KEY reuses JWT_SECRET_KEY**
   - **File**: `infra/terraform/main.tf` line 131
   - **Code**: `APP_SECRET_KEY = module.secret_manager.secret_ids["jwt_secret_key"]`
   - **Impact**: Both JWT signing and app encryption use the same secret. If one is compromised, both are compromised. Security best practice dictates separate secrets.
   - **Fix**: Create a dedicated `app_secret_key` secret in the secret-manager module.

3. **`.terraform.lock.hcl` not committed**
   - **Design**: Listed in the file changes table, expected to exist
   - **Reality**: Auto-generated by `terraform init`, but should be committed for deterministic provider version pinning
   - **Fix**: Run `terraform init` and commit the lock file

4. **Only coded tasks are marked as completed in tasks.md**
   - **Status**: 5 of ~30 tasks are checked (3.1-3.3 coded, 4.1-4.2 scripts, 5.0 scripts)
   - **Impact**: Most Phase 1, 2, 4, 5, 6 tasks (secrets population, image pushing, DNS cutover, decommission) remain unchecked. This is expected — many are ops tasks, not code — but should be tracked.

5. **Web Cloud Run service has no secret references**
   - **File**: `infra/terraform/main.tf` — no `web_secret_vars` passed to `module.cloud_run`
   - **File**: `infra/terraform/modules/cloud-run/main.tf` — references `var.web_secret_vars` in template
   - **Impact**: Currently no secrets are expected for the web service, so this defaults to `{}`. But if web needs secrets later, the Terraform wiring is missing.
   - **Fix**: Add `web_secret_vars` to the root module call, even if empty.

### 🟢 SUGGESTIONS (Nice to Have)

1. **Add ShellCheck to CI** — The shell scripts are well-written with `set -euo pipefail`, but there's no automated linting. Add a `shellcheck` step to the infra workflow.

2. **Remove `continue-on-error: true` from Terraform format check** — Currently `terraform fmt -check` has `continue-on-error: true`, which means format issues don't fail the build. Remove this to enforce formatting.

3. **DNS cutover script approach** — The `cutover-dns.sh` builds a YAML transaction file manually. The `gcloud dns record-sets transaction` command has a specific transaction workflow. Verify the manual YAML approach works with the `--transaction-file` flag.

4. **Document the host-based vs path-based routing decision** — Update the tasks.md and design.md to reflect that the load balancer uses host-based routing (subdomain separation) rather than path-based routing.

5. **Add Terraform validate step to PR checklist** — The infra workflow already does this, but document that all PRs touching `infra/` should include a Terraform plan.
